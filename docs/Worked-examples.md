# Worked examples: Firefox MSI and Notepad++ EXE

The current [Firefox](../examples/apps/firefox/app.json) and [Notepad++](../examples/apps/notepadplusplus/app.json) definitions use schema v3 while retaining native-v2 endpoint behavior: Windows 11 x64, SYSTEM and `DeployMode Auto`. The resolver/build path invokes the official PSADT 4.1.8 template adapter with generated metadata/action maps. Editable application snippets contain native calls and simple assignments; process handling comes from `AppProcessesToClose` and the stock welcome. The named profile omits the illustrative completion prompt; the adapter default retains it. Initialization, dispatch, error handling, modules and launcher remain preserved.

Historical research inspected exact release archives, verified 1,200 Evergreen definition-file hashes, performed live release discovery and checked the native-v2 sources. The old discovery records and `evidence/native-v2-example-validation.json` do not validate changed v3 inputs. Current checks are recorded separately in the [validation summary](../evidence/configuration-v3-validation.md). Offline fixtures and mocked packaging/publication do not establish real installer download/signature inspection, endpoint functionality, actual `.intunewin` creation, upload or assignment. Signer approval, external-policy acceptance and target group IDs must come from the operator's actual environment.

Firefox's stable label is `Current`. Its tagged definition obtains MSI/EXE hashes from Mozilla's release checksum listing. Do not invent filters for missing properties, take the first result, or cast every vendor version to `[version]`. These two examples accept numeric versions; other products need an explicit comparison policy. ## Definition and generated-input mapping

The [v3 definition schema](../schemas/application-definition.v3.schema.json) is strict JSON Schema draft 2020-12. Both `app.json` files use `toolkit.profile=official-4.1.8-native-v2`, definition revision 3, package revision `02` and script version `1.1.0`. Editable Install, Uninstall and Repair scripts are the sole owners of executable commands and installer arguments. Discovery writes a separate `DiscoveredRelease`; resolution checks local installer evidence and binds that release into generated metadata/detection. Keep volatile URLs and acceptance outcomes in records, not the definition. A pinned selection requires its exact target; it does not enable historical lookup through Evergreen.

| Authored/resolved input | Population destination or external concern |
|---|---|
| Publisher, product name, resolved release version, architecture/language, toolkit package revision/script author | `AppVendor`, `AppName`, `AppVersion`, `AppArch`, `AppLang`, `AppRevision`, `AppScriptAuthor` in generated metadata and the template's `$adtSession` |
| `toolkit.version`, `toolkit.profile` | Verified official distribution and adapter compatibility contract; never overwrite the script's framework version field |
| Success/reboot policy | `AppSuccessExitCodes=@(0)`, `AppRebootExitCodes=@(1641,3010)`; Intune return-code rules are configured separately |
| SYSTEM/admin requirement | `RequireAdmin=$true`; Intune `InstallExperience=system` is separate |
| `actions` paths and editable scripts | Three trusted Main snippets referenced from `app.json`; build snapshots them beside `actions.generated.json` and inserts them only at matching task locations |
| Running processes | `AppProcessesToClose=@(@{Name='firefox';Description='Mozilla Firefox'})` or the corresponding `notepad++`/`Notepad++` object |
| `payloads.installer.destination` and accepted bytes | Build stages the reviewed installer as `Files/Firefox.msi` or `Files/NotepadPlusPlus.exe` and records its hash |
| Firefox policy prerequisite | `deployment.externalPolicyPrerequisites`: Intune `DisableAppUpdate=true`; separate acceptance evidence must confirm enforcement, with no packaged policy writer |
| Detection, requirements, dependencies, assignments | Intune configuration outside the deployment template; detection scripts have no toolkit dependency |
| Deferral policy | `template-default`; official welcome permits three installation deferrals when interactive; no authored custom deadline |
| Intune time limit | `maximumInstallationTimeInMinutes=120`, configured outside the template |
| Downgrade handling | `vendor-default`; no custom downgrade guard or promise that the vendor rejects downgrades |
| Hashes, resolved URLs, module/app-definition versions, build ID and app ID | Release/build/publication records outside package source |

The [configuration reference](Configuration-reference.md) identifies each field's owner and consumer. Build provenance records exact source snapshots and hashes; generated metadata/action maps are outputs, not editable competing authorities. Display metadata is an engineering choice, not proof of binary identity. Approve signer policy independently using vendor evidence and inspect the actual file. A self-computed hash identifies bytes; comparison with an upstream hash adds integrity evidence; neither substitutes for publisher approval.

## Discovery, acquisition and release binding

Follow [Prepare a release](Prepare-release.md) and the [walkthrough](Getting-started.md) for executable commands. The sequence is:

1. Copy the application's `app.json`, editable actions and detection template into a fresh nonsynchronized release workspace.
2. Run discovery with `-DefinitionPath` and the pinned Evergreen module/definitions. It requires exactly one selected installer and does not download it. `-RecipePath` is only a v3-definition alias.
3. Acquire the selected installer manually, inspect the bytes/signature/product identity and complete [installer evidence](../examples/installer-evidence.example.json). Null approvals remain pending; there is no `identityReviewStatus` switch.
4. Resolve `-DefinitionPath`, `-ReleasePath`, `-InstallerPath` and `-EvidencePath`. Save the returned `ResolvedBuild` with `Write-AppJsonAtomic`.
5. Preview and explicitly execute `Build-Application.ps1` with that resolved record, the pristine template and a fresh destination. The builder snapshots sources, generates internal adapter inputs, stages declared payloads and writes the build manifest plus standalone detection.

Keep Evergreen's module and definitions pinned throughout the attempt; the discovery entry point does not run `Update-Evergreen`. The published `2610.2859.0` downloader does not have the newer default-branch `-VerifyChecksum` option, and its internal error/existing-file behavior needs independent postconditions. A returned download path is not approval. The current documented workflow uses manual acquisition and explicit local validation rather than presenting the helper as a complete download gate. [Published module](https://www.powershellgallery.com/packages/Evergreen/2610.2859.0), [newer default-branch downloader](https://github.com/EUCPilots/evergreen-module/blob/56699ec976e77a8031f1d93fc8c5eda22ceae085/Evergreen/Public/Save-EvergreenApp.ps1).

Check definition selectors and expected identity against the downloaded payload. For MSI, inspect ProductName, ProductVersion, ProductCode, UpgradeCode, Manufacturer, ProductLanguage and SummaryInformation without installation; never use `Win32_Product`. An EXE bootstrapper's own PE architecture/version can differ from its payload, so verify installed behavior in a lab. These examples do not represent installer-derived values as already accepted.

Release binding is implemented by the resolver and detection binder. Do not hand-edit metadata or version literals, and do not change `latest` policy to `pinned` after discovery. The retained release fixes the chosen version; generated metadata, detection and publication use it consistently. Source drift after resolution fails the build. A change requires explicit re-resolution and a new destination, not edits to finalized outputs.

Current offline reference copies belong under the ignored `generated-examples/psadt-4.1.8-config-v3/`. Their explicit fixture bytes are not vendor installers and cannot be published. Earlier `generated-examples/psadt-4.1.8-auto-v2/` copies and frozen detection/metadata are historical records. Nonempty generated `AppName` still disables zero-config MSI while preserving those framework blocks. Both examples remain Main only; general coverage of all nine native task locations lives in separate adapter tests.

## What runs on endpoints

Firefox's MSI wraps the full EXE installer, does not register a normal Windows Installer product, and does not support MSI `/x` or `/f`. The example installs through `Start-ADTMsiProcess`, uninstalls through `uninstall\helper.exe /S`, and explicitly rejects Repair with 69001. **An MSI installer file does not justify MSI product-code detection for this product.** A conventional MSI that registers a product would instead use its inspected product identity and validated MSI uninstall/repair semantics. [Mozilla MSI implementation](https://firefox-source-docs.mozilla.org/browser/installer/windows/installer/MSI.html), [supported MSI options](https://support.mozilla.org/en-US/kb/deploy-firefox-msi-installers), [silent uninstall](https://support.mozilla.org/en-US/kb/silently-install-uninstall-firefox-enterprise).

Firefox vendor properties are passed with `-AdditionalArgumentList`, retaining PSADT's default MSI `REBOOT=ReallySuppress /QN` and logging. They include `REMOVE_DISTRIBUTION_DIR=false` because the vendor default removes the distribution directory during installation. This preserves existing files; it does not establish effective update policy. Disabling the maintenance service alone does not disable application updates. [MSI property reference](https://support.mozilla.org/en-US/kb/deploy-firefox-msi-installers), [PSADT 4.1.8 MSI defaults](https://github.com/PSAppDeployToolkit/PSAppDeployToolkit/blob/4.1.8/src/PSAppDeployToolkit/Config/config.psd1).

Firefox `DisableAppUpdate=true` must be deployed and verified separately through Intune. The definition declares that requirement; release acceptance must provide matching policy evidence. It does not create or assign the policy. Review existing policy ownership before migrating: Mozilla states that its JSON policy method does not work when Group Policy manages Firefox, so preserving an existing policy file does not guarantee its unrelated settings remain effective after a policy-source change. Verify all required policies on the endpoint. [DisableAppUpdate](https://firefox-admin-docs.mozilla.org/reference/policies/disableappupdate/), [Mozilla policy-source guidance](https://support.mozilla.org/en-US/kb/customizing-firefox-using-policiesjson).

Notepad++ uses `Start-ADTProcess -ArgumentList '/S /noUpdater ...' -WaitForChildProcesses -ExitOnProcessFailure`. NSIS `/D=` is last and unquoted. The inspected installer deselects both Auto-Updater and Plugins Admin when `/noUpdater` is supplied. The deployment has no custom leftover-updater check or removal. Existing installations require an approved migration and endpoint verification; `/noUpdater` alone is not proof that every legacy updater is removed. Plugins and user settings need business acceptance. [Installer v8.9.8.1](https://github.com/notepad-plus-plus/notepad-plus-plus/blob/v8.9.8.1/PowerEditor/installer/nppSetup.nsi), [component source](https://github.com/notepad-plus-plus/notepad-plus-plus/blob/v8.9.8.1/PowerEditor/installer/nsisInclude/binariesComponents.nsh), [NSIS command-line reference](https://nsis.sourceforge.io/Docs/Chapter3.html#installerusage).

Native `Auto` uses Interactive mode when a configured process is running and an interactive user session is available, and Silent mode when none of those processes are running. Session/OOBE conditions can also select Silent. The default installation welcome offers three deferrals; uninstall uses its native 60-second close countdown. Toolkit behavior can close processes, including a process that starts after Auto selected Silent. These examples do not promise retry-without-closing or protection of unsaved work beyond toolkit defaults. The frontend help's process description is stale; the tagged session implementation establishes the behavior. [PSADT 4.1.8 session logic](https://github.com/PSAppDeployToolkit/PSAppDeployToolkit/blob/4.1.8/src/PSADT/PSADT/Module/DeploymentSession.cs#L795-L838).

The application snippets have no custom downgrade guard or post-install assertions. Intune detection normally skips a same/newer qualifying installation; a direct wrapper invocation relies on vendor behavior, which must be tested. Uninstall invokes each fixed vendor EXE directly: a missing uninstaller follows native PSADT failure handling, rather than custom absent-app success. Repair still uses native logging and `Close-ADTSession -ExitCode 69001` to reject an unsupported action explicitly.

`-ExitOnProcessFailure` preserves installer failures by closing the session with the process failure code. Reboot-required results remain tracked by the session and standard final `Close-ADTSession`. Do not suppress reboot pass-through or append an unconditional `exit 0`. The complete desired Intune mapping is 0/1707=success, 3010=softReboot, 1641=hardReboot, 1602/1618=retry, and 60001/60008/69001=failed. Native interactive deferral returns 1602; UI timeout uses 1618. IntuneWin32App already supplies 0/1707/3010/1641/1618, so publication passes only extra codes through `-ReturnCode`, avoiding duplicate defaults. Configure the Intune installation-time limit to **120 minutes**. Toolkit success codes, UI deferral settings, Intune retries and runtime limits are separate controls. [PSADT 4.1.8 source](https://github.com/PSAppDeployToolkit/PSAppDeployToolkit/tree/4.1.8), [published IntuneWin32App module](https://www.powershellgallery.com/packages/IntuneWin32App/1.5.0).

## Packaging and detection are separate

`Package-Application.example.ps1 -BuildManifestPath` previews by default, verifies the frozen build inventory and pinned tools, and derives settings from the retained profile. It selects **`Invoke-AppDeployToolkit.exe`**, includes the complete package `Source`, keeps output outside that tree, and rejects source drift. Manifest mode verifies the extracted IntuneWin32App module against its pinned package archive. Only explicit `-Execute` runs Content Prep; it creates a `.intunewin` and `package-manifest.json` without tenant access. See the [walkthrough](Getting-started.md#5-preview-and-create-the-package) for the supported commands and archive layout.

Publication preparation consumes that package manifest and separate endpoint/business/prerequisite acceptance. A saved `PublicationRequest` carries the frozen commands, metadata, detection and artifact hashes into publisher preview. The named profile's effective commands are:

```text
Invoke-AppDeployToolkit.exe -DeploymentType Install -DeployMode Auto
Invoke-AppDeployToolkit.exe -DeploymentType Uninstall -DeployMode Auto
```

Each authored `Detect.template.ps1` has a single reviewed version slot. Resolution/build bind it to the accepted release and emit standalone UTF-8 BOM `Detect.ps1`, independent of PSADT. Historical native-v2 detector hashes remain separate compatibility evidence. The generated detector checks the actual executable, x64 PE identity, 64-bit machine registration, and installed version **at least** the packaged version. Firefox additionally checks en-US registration and installed `app.update.channel=release`; the file is read as data. Missing, conflicting or unrecognized identity fails closed. Mozilla documents the channel file separately from normal updated payloads. [Mozilla channel concepts](https://firefox-source-docs.mozilla.org/toolkit/mozapps/update/docs/Concepts.html), [MAR channel-file path](https://firefox-source-docs.mozilla.org/toolkit/mozapps/update/docs/MarFiles.html).

Run detection in 64-bit context. Success emits output and exits 0; every not-detected path exits 1 without output. Do not dot-source these scripts into an orchestration shell, because they intentionally exit. Validate the exact registry shape, numeric file-version mapping, channel file and language behavior on representative clean/upgrade installations before allowing publication. These checks deliberately ignore a wrapper-completed registry marker. Configuration compliance is a separate policy/test concern, so changing only configuration may require a separate remediation/update design.

**Existing-fleet adoption prerequisite:** a same-version or newer installation satisfying detection causes Intune to skip the wrapper. That does not establish central update control. Enforce and verify the separate Firefox Intune policy across the fleet. Existing Notepad++ installations with an updater need an approved migration or reinstall plan that preserves or upgrades their version. Do not use downgrade as a configuration-remediation strategy. Central update control must be demonstrated separately before adoption.

These definitions support fresh installation or upgrade. **Update-only** would require a separately implemented applicability rule for an existing supported installation, independent of final-version detection; the current schema rejects that alternative. A required assignment can therefore install on previously uninstalled devices. Per-user installs, other languages, x86/ARM64, ESR/Beta and multiple simultaneous editions need distinct definitions, supported profiles and tests; the examples are not generalized to them.

Acceptance requires fresh install, supported upgrade, same/newer version, wrong architecture/language/channel, missing component, absent app, uninstall, unsupported repair, running app, no logged-on user, restart outcomes, and failed/partial installation. Test the exact launcher commands in a disposable SYSTEM-context Windows lab and then test user workflows. Packaging success alone satisfies none of those endpoint or business-function checks.
