# Intune publication, updates, and operations

The dependency research baseline is November 3, 2026, America/Los_Angeles. The repository now implements local version 3 definition resolution, immutable build/package records and publication-request preparation, with offline and mocked checks. No actual packaging-tool execution, Intune connection, tenant mutation, installer execution or endpoint deployment is established by those checks. The supported profile remains Windows 11 x64, SYSTEM, Auto, Intune-controlled updates and a new unassigned Intune app per approved release. The tenant cloud must be confirmed before execution.

## The wrapper changes the Intune contract

For both MSI and EXE applications, select **`Invoke-AppDeployToolkit.exe`** as the Content Prep Tool setup entry point. Publish using the IntuneWin32App **EXE parameter set**, selected by supplying both command lines:

```text
Invoke-AppDeployToolkit.exe -DeploymentType Install -DeployMode Auto
Invoke-AppDeployToolkit.exe -DeploymentType Uninstall -DeployMode Auto
```

The package's selected setup file is now the launcher. Content Prep's automatic MSI extraction is documented for an MSI setup file; do not treat the wrapper package as though its metadata identifies the embedded MSI. Extract the downloaded MSI's ProductCode/ProductVersion/Manufacturer independently and choose detection for the installed product. Never select the MSI merely to obtain metadata while silently assuming the PSADT wrapper remains the effective entry point. [Microsoft packaging guidance](https://learn.microsoft.com/intune/app-management/deployment/create-win32-package), [Add function's MSI and EXE branches](https://www.powershellgallery.com/packages/IntuneWin32App/1.5.0/Content/Public%5CAdd-IntuneWin32App.ps1)

**Microsoft support boundary:** current Intune documentation requires silent installation and explicitly does not support forced interaction with the signed-in session through ServiceUI or similar techniques. The user-selected Auto commands exercise PSADT's native behavior, which can display UI; they do not acquire Microsoft support merely because no ServiceUI wrapper is used. Validate this chosen behavior in isolated SYSTEM-context tests before considering publication. [Microsoft Win32 management](https://learn.microsoft.com/intune/app-management/deployment/win32)

The samples populate native `AppProcessesToClose` with `firefox` or `notepad++`. PSADT 4.1.8 resolves Auto during session initialization: no matching process selects Silent, while a matching process selects Interactive unless an earlier native condition has selected Silent, including OOBE/ESP or a noninteractive SYSTEM session without a usable signed-in user. This comes from the tagged implementation; the frontend's Auto help text is inverted. It is not continuous process protection. A process starting after Silent selection can be force-closed by the native welcome; a process exiting after Interactive selection does not guarantee that all prompts disappear. Native behavior can close processes without saving data. The samples add no custom process guards, force-close policy, or relaunch protection. [Tagged deployment-session implementation](https://github.com/PSAppDeployToolkit/PSAppDeployToolkit/blob/4.1.8/src/PSADT/PSADT/Module/DeploymentSession.cs), [native welcome implementation](https://github.com/PSAppDeployToolkit/PSAppDeployToolkit/blob/4.1.8/src/PSAppDeployToolkit/Public/Show-ADTInstallationWelcome.ps1)

The stock Install welcome retains three deferrals, disk-space checking, and a persistent prompt; stock Uninstall and Repair retain the 60-second close-process countdown. Three deferrals are opportunities to defer, not three days or a custom deadline. The native prompt timeout is 3,300 seconds (55 minutes). Set `-MaximumInstallationTimeInMinutes 120` in the Intune publisher to leave installation time beyond that prompt budget; the module otherwise defaults to 60 minutes and accepts integers 1–1,440. The illustrative stock completion message is omitted through the adapter's explicit option, with no replacement UI. Repair remains unsupported and is not published as an action: its native welcome can run before the sample logs the unsupported operation and exits 69001. [Official template](https://github.com/PSAppDeployToolkit/PSAppDeployToolkit/blob/4.1.8/src/PSAppDeployToolkit/Frontend/v4/Invoke-AppDeployToolkit.ps1), [toolkit configuration](https://github.com/PSAppDeployToolkit/PSAppDeployToolkit/blob/4.1.8/src/PSAppDeployToolkit/Config/config.psd1), [published timeout parameter](https://www.powershellgallery.com/packages/IntuneWin32App/1.5.0/Content/Public%5CAdd-IntuneWin32App.ps1)

Do not pass PSADT's `-SuppressRebootPassThru` if Intune must receive reboot-required status. Do not copy v3-era `-AllowRebootPassThru` guidance into 4.1.8. Installation commands in the default template must deliberately choose error behavior: `-ExitOnProcessFailure` on the relevant PSADT process function preserves native failures; an exception reaching the stock template catch returns 60001. Verify these behaviors using the actual launcher, including prerequisites that request reboot. See the version-specific PSADT packaging standard accompanying this document.

IntuneWin32App Add includes defaults **0/1707 → success, 3010 → softReboot, 1641 → hardReboot, 1618 → retry**. Its `-ReturnCode` parameter **appends** entries rather than replacing these defaults; pass only additional codes. The example adds **60001/60008/69001 → failed** and **1602 → retry** for native deferral. The preview exposes all nine unique effective mappings while execution supplies only the four additional entries. The inherited 1618 retry mapping handles the native timeout; do not add it again. Microsoft describes retry as three attempts with five-minute waits, so default deferral opportunities can be consumed within a short retry cycle. A deferral is never installation success. Soft reboot permits subsequent Win32 installations; hard reboot blocks subsequent Win32 installations until reboot. [Module default mappings](https://www.powershellgallery.com/packages/IntuneWin32App/1.5.0/Content/Private%5CGet-IntuneWin32AppDefaultReturnCode.ps1), [Microsoft return-code behavior](https://learn.microsoft.com/intune/app-management/deployment/add-win32#step-2-program)

Detection is an independent endpoint script or native MSI/file/registry rule, not a PSADT completion marker. Intune custom detection requires **exit 0 and nonempty STDOUT**; STDERR makes detection fail even when those two conditions are met. Multiple native detection rules are ANDed. Requirements determine applicability; they must not be confused with detection. A version floor may permit a newer installed release, but a changed MSI ProductCode can still defeat an otherwise valid version comparison. Match architecture, language, edition/channel and all necessary components. [Microsoft detection requirements](https://learn.microsoft.com/intune/app-management/deployment/add-win32#step-4-detection-rules)

## Current local-to-tenant contract

| Input/operation | Implemented boundary |
|---|---|
| `app.json` plus editable action/detection sources | One authored definition. Native installer arguments live only in the scripts. The active workflow rejects legacy recipe schema version 2. |
| `ResolvedBuild` → `ApplicationBuild` | Accepted local installer evidence, resolved version, generated metadata, bound standalone detection and reviewed source inventories. Build execution creates a fresh local artifact; it does not run deployment code. |
| `ApplicationBuild` → `ApplicationPackage` | Packaging previews locally; explicit execution invokes the pinned utility. The package manifest retains its hash, frozen definition/profile, detector, build identity and `packagingTools` provenance. |
| `Prepare-ApplicationPublication.ps1` | Reads that package manifest and optional acceptance. Returns a sealed request without writing files. No acceptance means unready; fixture packages are always unready. |
| `PublicationRequest` → publisher `-RequestPath` | Preview rechecks local hashes without importing/authenticating/writing. Execution revalidates the request against retained artifacts and evidence before entering the existing tenant mutation path. |
| `State` and pilot assignment | Separate tenant/client/group inputs, operation journal and returned app/content IDs. Assignment remains an explicit operation; production promotion remains manual. |

The request carries the package's frozen display metadata, command profile, requirements, detection and return codes. Publication does not reread a mutable application definition or rediscover a release. The marker's `ReleaseId` is the content-based `buildId`; a working-directory GUID is only a local attempt name.

[Release acceptance](../schemas/release-acceptance.v1.schema.json) must match application/build/package/final detection hashes, name and date endpoint/business reviewers, reference the actual report files by hash, and confirm every declared prerequisite using its stable requirement hash. The [pending example](../examples/release-acceptance.example.json) grants no approval. Record hashes detect inconsistency; they are not digital signatures or authenticated reviewer attestations. Human review of the underlying evidence remains required.

Optional signed detection is a separate copy of the generated detector. Preparation checks a valid Authenticode signature, unchanged body except an appended recognized signature block/trailing newlines, and unchanged bytes during verification. Acceptance binds the final signed hash. Request preview performs no signature lookup; explicit preparation with `-SignedDetectionPath` and execution do. The current build workflow has no supported stage for signing the generated PSADT script after its source inventory is frozen.

The publisher retains an explicit legacy parameter set for historical callers; the current walkthrough uses `-RequestPath`. The sets cannot be mixed. Legacy calls do not gain the new acceptance contract automatically. Historical v2 configuration fixtures are retained under [tests/fixtures/legacy-v2](../tests/fixtures/legacy-v2/migration-manifest.json), not as active authoring inputs.

## Authentication and permissions

Manual use: a dedicated public-client app registration, interactive delegated authentication, an appropriate Intune role, administrator consent as required, and the localhost redirect expected by 1.5.0. App registration creation is a future administrative prerequisite, not something performed in this research. Use a separate publisher process; build-only work needs no tenant credentials. The examples request `DeviceManagementApps.ReadWrite.All` and `offline_access`, not every scope in the module default array. [Published authentication implementation](https://www.powershellgallery.com/packages/IntuneWin32App/1.5.0/Content/Public%5CConnect-MSIntuneGraph.ps1)

Before the first tenant execution, have the administrator:

1. Confirm commercial-cloud compatibility and register a dedicated application for the organization. Record Directory (tenant) ID and Application (client) ID.
2. Add the **Mobile and desktop applications** platform with **`http://localhost`** as the redirect URI. The inspected delegated implementation opens a system browser using a dynamically selected localhost port; no client secret is used.
3. Grant delegated **`DeviceManagementApps.ReadWrite.All`** with the required administrator consent. The examples also request **`offline_access`**.
4. Assign the operator appropriate Intune **Mobile apps: Read, Create, Update, Assign** permissions and the intended scope groups/tags. Confirm licensing and tenant approval requirements.
5. Approve the explicit pilot group ID and membership, observation period, acceptance thresholds and incident owner. Group-name/scope-tag/filter lookup is outside the current examples.

[Microsoft desktop registration](https://learn.microsoft.com/en-us/entra/identity-platform/scenario-desktop-app-configuration) · [Published delegated flow](https://www.powershellgallery.com/packages/IntuneWin32App/1.5.0/Content/Private%5CNew-DelegatedAccessToken.ps1) · [Intune RBAC](https://learn.microsoft.com/en-us/intune/intune-service/fundamentals/role-based-access-control-reference). Consent does not replace delegated Intune RBAC.

| Operation | Permission design |
|---|---|
| App creation/content publication/app assignment | `DeviceManagementApps.ReadWrite.All`, delegated now or application later. Confirm endpoint-specific consent and the delegated user's Intune RBAC. |
| Read-only inventory/reconciliation | Separate identity with `DeviceManagementApps.Read.All` where supported; preview itself needs no identity. |
| Resolve scope-tag names | Add `DeviceManagementRBAC.Read.All` for the module's lookup. |
| Resolve an existing assignment filter | Add `DeviceManagementConfiguration.Read.All`; creating/changing filters is outside this design. |
| Resolve group names or inspect group members | Add only the appropriate directory read permission for the chosen properties/operation. `GroupMember.Read.All` and `Group.Read.All` are supported group-read choices; the latter is broader. |
| Create dependency/supersedence relationships | App-management Graph permission plus appropriate delegated Intune RBAC, including Mobile apps **Relate**. |

The Graph documentation lists alternative sufficient permissions, not a requirement to grant every listed permission. The module README's broad default scopes are not a least-privilege specification. Its `Get-IntuneWin32AppAssignment -ID` resolves group names and therefore adds directory-reading needs. The examples instead read the assignments endpoint directly using the authenticated header and supplied group IDs. [Create Win32 app](https://learn.microsoft.com/graph/api/intune-apps-win32lobapp-create?view=graph-rest-1.0), [assign](https://learn.microsoft.com/graph/api/intune-shared-mobileapp-assign?view=graph-rest-beta), [scope-tag lookup](https://learn.microsoft.com/graph/api/intune-rbac-rolescopetag-list?view=graph-rest-beta), [filter lookup](https://learn.microsoft.com/graph/api/intune-policyset-deviceandappmanagementassignmentfilter-list?view=graph-rest-beta), [group reads](https://learn.microsoft.com/graph/api/group-get?view=graph-rest-1.0), [relationship permissions](https://learn.microsoft.com/intune/app-management/deployment/configure-win32-supersedence#prerequisites)

Later unattended use: a separate confidential-client registration and certificate-based client credentials. `-ClientCert` takes an `X509Certificate2` object with its private key, not a thumbprint string. Store the key in the automation identity's protected certificate store, restrict its private-key ACL, monitor expiry, and overlap old/new credentials during rotation. A secret fetched just in time from an approved secret store is supported but is the second choice; do not put it in recipes, scripts, transcripts, arguments, or source control. Client-credential flows use the application's consented permissions; `-Scopes` does not reduce an already overprivileged application token. [Published certificate and secret flows](https://www.powershellgallery.com/packages/IntuneWin32App/1.5.0/Content/Public%5CConnect-MSIntuneGraph.ps1)

1.5.0 has no public managed-identity, federated-assertion, external-access-token, or cloud-environment parameter. Its Graph and authority URLs target the global cloud. Do not promise workload-federation/managed-identity or sovereign-cloud compatibility by setting undocumented global variables. A future supported adapter or different publishing implementation would need separate design and tests. **The examples require `-ConfirmedCommercialCloud` with execution because the user's cloud is unknown.**

Token refresh is not assumed reliable merely because it is advertised. The published Graph helper attempts refresh with `$Global:AccessToken.client_id`, while the inspected delegated/device-code token constructors do not populate that property. This is a **source-identified risk, not a reproduced tenant failure**. Explicit `Connect-MSIntuneGraph -TenantID ... -ClientID ... -Refresh` uses the supplied ID; certificate/secret sessions must reacquire a token rather than use delegated refresh tokens. Test expiry during long uploads and fail before unsafe retries. Issue 208 remains an open report about refresh; the inspected package adds a `RefreshToken` property, so distinguish that historical symptom from the separate client-ID observation. [Published helper](https://www.powershellgallery.com/packages/IntuneWin32App/1.5.0/Content/Private%5CInvoke-MSGraphOperation.ps1), [delegated constructor](https://www.powershellgallery.com/packages/IntuneWin32App/1.5.0/Content/Private%5CNew-DelegatedAccessToken.ps1), [issue 208](https://github.com/MSEndpointMgr/IntuneWin32App/issues/208)

Multi-Admin Approval is another environment question. Microsoft's current guidance restricts uploading PowerShell installer scripts during app creation when MAA is enabled. The examples use a packaged launcher command, not the new separately uploaded PowerShell-installer feature; do not generalize that specific restriction into a claim that MAA cannot affect any other app operation. Confirm the tenant's approval policy before publication. [Microsoft script-installer/MAA guidance](https://learn.microsoft.com/intune/app-management/deployment/win32#powershell-script-installer)

## Release strategy and controlled updates

**Default: one Intune app per approved immutable release.** Test the generated deployment/detection on isolated machines, package and bind acceptance, publish unassigned, assign an approved pilot group, evaluate results, then add production targeting to the **same tested app ID and content**. Keep app-object, assignment and endpoint-installation state separate. Do not rebuild between pilot and production.

| Concern | New app per release | Replace content/metadata on existing app |
|---|---|---|
| App ID | New ID; stored against the release. | Stable ID. |
| Assignments | Explicitly recreated/promoted; old and new targeting must be reconciled. | Existing targeting immediately applies to the changed app. |
| Pilot isolation | Pilot can remain separate while production continues using the prior object. | A shared production object cannot expose different content to pilot and production; use a separate pilot object if this exception is selected. |
| Detection and commands | Reviewed as one release manifest. | Content and metadata changes are separate operations and can leave a mixed state. |
| Company Portal | Control visibility/naming of old releases; supersedence changes availability. | Stable listing and user-facing identity; existing detection still governs reinstall/update. |
| Dependencies/supersedence | Relationships use IDs; review and update deliberately; limit chain growth. | References remain, but dependency consumers receive the changed behavior. |
| Autopilot/ESP | ID references must be reviewed when promotion changes which app is required. | Stable references simplify administration but broaden impact; test enrollment separately. |
| Recovery | Stop new targeting and preserve previous evidence; downgrade remains vendor-dependent. | Restore prior content, detection, commands and metadata together; installed devices still need a tested recovery procedure. |
| Retention | More objects; retain previous releases and inspect incoming references before cleanup. | Fewer objects; preserve every prior external artifact because tenant content history is not your backup. |

Use in-place replacement only when maintaining an existing ID materially matters and a separate test object plus coordinated change window are acceptable. Microsoft distinguishes in-place content/metadata changes from supersedence and limits supersedence chains to ten related nodes. For normal vendor-supported upgrades, let the newer installer upgrade the old product; select uninstall-before-install only when the vendor and tests require it. [Microsoft supersedence behavior](https://learn.microsoft.com/intune/app-management/deployment/configure-win32-supersedence)

**Initial install versus update-only:** a required assignment ordinarily installs the app on eligible devices where detection is false. For update-only operation, add a requirement that positively identifies a supported installed product/version/architecture/channel; an absent app is not applicable. Keep that requirement separate from target-version detection. Available-app supersedence auto-update has narrower conditions involving prior Company Portal consent/installation and available targeting; it is not a generic installed-software targeting feature. Assignment changes can remove that consent. [Microsoft available-app auto-update](https://learn.microsoft.com/intune/app-management/deployment/configure-win32-supersedence#use-auto-update-with-app-supersedence)

Because the chosen policy is Intune-controlled updates, each application definition declares its update policy and prerequisites. Firefox's `DisableAppUpdate` policy is managed separately through Intune; the deployment contains no policy JSON payload or merge operation. Its confirmation requires evidence of the actual policy assignment and effective endpoint setting. Notepad++ retains `/noUpdater` in its editable Install script; acceptance must cover updater/component behavior and the declared legacy-updater/Plugins Admin decision. Publication preparation checks matching prerequisite evidence, not the tenant policy itself. The definitions declare `vendor-default` downgrade handling; no custom downgrade guard is added. Independent detection accepts a qualifying version greater than or equal to the target. Retained packages support investigation and recovery preparation, not a guarantee of downgrade, preserved data formats or reverse migration.

## State, retries, and operational acceptance

Keep version labels as strings and use an application-specific documented comparator; do not coerce all vendor versions to `[version]` or sort them lexically. Record separately: discovered upstream release; selected/downloaded installer; build fingerprint; tested artifact; published app ID/content version; pilot/production assignment; and per-device observed installation/functionality. A deployed version is a set of observations, not one global Boolean.

Keep distinct records for discovery, installer evidence, resolved build, generated build, package, acceptance and publication request. Retain full definition hashes for provenance. The discovery fingerprint covers selection intent and provider pins; build identity covers effective deployment metadata, actions, detection/support/payload inputs and generator/dependency provenance. A changed installer hash at the same version or changed deployment behavior creates a different build. Rollout-only state does not change the payload identity. Final package/detection hashes are separate from input identity; equal inputs do not promise byte-identical encrypted package recreation.

The immutable package/request must remain separate from `State`: tenant/client/group IDs, application/content IDs, assignment observations, operator journal and promotion decisions are operational records. Store only unsigned source URLs that pass the validated URL policy; never persist signed upload/download URLs, tokens, credentials or private keys.

Use JSON records and an operation journal on nonsynchronized local storage. Local record writes are exclusive and atomic; they do not implement durable tenant-operation locking or recovery. Allow one operator per application/tenant until a proper writer lock exists. Before retrying an uncertain write, reconcile the stored app ID and exact release marker; ambiguous duplicates halt for review. Create/upload/commit are not transactional. Preserve every known ID and partial result; a missing local result does not prove the app was never created. The examples cannot resume uploads. Have an administrator decide repair or controlled cleanup after inspecting content and assignments; do not delete an app merely because a command timed out.

The module uses Graph **beta** for central app operations. Its HTTP helper implements pagination, Retry-After handling and transient retries, but it cannot make an ambiguous POST idempotent. The orchestration layer still owns bounded retry policy, token reacquisition, timeout budgets, and reconciliation. Microsoft supports Intune beta APIs while recommending v1.0 when available because beta changes more frequently. Keep the module pinned and contract-test upgrades. [Published HTTP helper](https://www.powershellgallery.com/packages/IntuneWin32App/1.5.0/Content/Private%5CInvoke-MSGraphOperation.ps1), [Microsoft beta guidance](https://learn.microsoft.com/graph/api/intune-shared-mobileapp-assign?view=graph-rest-beta)

Toolkit changes do not imply mass repackaging automatically. A routine template upgrade normally applies to future releases after regression testing. Rebuild existing applications when a security/compatibility fix, current deployment failure, or required behavior change justifies it; create a new build identity and repeat validation even when the application version stays unchanged. Preserve the old artifact and its source manifest. The application owner approves business-function acceptance; the packaging engineer owns recipes and technical tests; the Intune operator owns targeting, monitoring, incident containment and cleanup.

The publisher, publication preparation and pilot example have offline/mock coverage, not live tenant acceptance. They preserve explicit preview/mutation boundaries. Request publication verifies artifacts and locally supplied acceptance, the setup filename, a release marker, committed content and no assignments. Assignment rejects pre-existing targeting rather than reconciling it automatically. Durable tenant journaling, distributed locking, resumable uploads, authenticated approvals, comprehensive retries, policy discovery and production promotion remain unimplemented.
